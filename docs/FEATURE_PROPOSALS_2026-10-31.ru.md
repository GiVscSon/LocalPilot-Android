## Приоритет A. Смена сцены/ROI: сначала только обнаружение и безопасное предложение

**Гипотеза пользователя:** после переключения из 6×6 «Нащупай ход» в Hexa/Tower остаётся ROI прошлой игры и возникает `REBOUND_R...`. На текущем `PilotService` есть явный `REBOUND_ROI_OUTSIDE_WINDOW`, ручной выбор игры, сброс ROI при изменении профиля и проверки перепривязки.

**Новая функция:** `SceneSignature` сравнивает *несколько* независимо свежих кадров по маске внутреннего игрового поля, геометрии, распределению объектов/структуры и временной стабильности. На вероятной смене игры: `STOP`, отзыв permit, сброс устаревшего ROI/палитры в сессии, уведомление **«Похоже, игра изменилась. Выберите профиль и область»**. Никаких жестов. Не переключать ROI на весь экран и не выбирать игру автоматически по одному отклонению RGB-гистограммы 45%: это может быть каскад, экран результата, анимация, меню или реклама.

**Тесты:** синтетические переходы сцены с неизменным окном; яркая анимация без смены игры (не должна перепривязывать); смена геометрии окна; панель перекрывает ROI; сохранение защищённого 6×6 swap и отсутствие ввода после отказа. Решающая диагностика: frameAt, window epoch, old/new ROI, reason.

## Приоритет A. Debug HUD чтения без влияния на само чтение

Только явное opt-in **«Диагностика зрения»** в существующем меню, а не автоматическое включение в Soft Vision. Показывать центры прочитанных клеток, reason для UNKNOWN/PROTECTED, доказанный центр launcher, силу уверенности и **планируемый** (но не выполненный) жест.

**Сильный риск:** `FLAG_NOT_TOUCHABLE` не гарантирует отсутствия оверлея на screenshot. Не опираться на недоказанный публичный API `setSkipScreenshot(true)`; выполнить подтверждённый lifecycle: hide/remove overlay → дождаться committed layout/fresh frame → capture → show. Если это не гарантируется на конкретном API30/35/36, HUD запрещается на время захвата. Индикация должна исчезать при STOP, не поглощать касания и не закрывать кнопки игры.

**Приёмка:** эталонные кадры без HUD и с диагностикой дают идентичные CV хэши/результаты; контрольные тесты у устройств и на API30/35/36; read-only режим без жестов; bounded число точек и ресурсное ограничение.

## Приоритет B. Динамический early-settle для таймерной сетки

**Уже существует:** `GridPuzzleSession` использует `FRESH_MS=300`, `SETTLE_MS=180`, `STABLE_MS=80`, два свежих идентичных post-ACK наблюдения и action-specific witness (особенно для swap). `responseTimeoutMs` стандартно 2500мс — **дедлайн отказа, а не обязательная задержка перед каждым новым ходом**. Предложение «убрать фиксированные 1500мс» нельзя принимать как диагноз без wall-clock trace.

**Измерить сначала:** от dispatch до ACK, первого post-ACK кадра, второго идентичного поля, решения и следующего dispatch; счётчики stale/retry, средний p50/p95 цикла с учётом ожиданий. Если планировщик действительно чрезмерно замедляет этап, сделать адаптивный capture/pacer шаг 180–220мс *после ACK*, не отменяя `SETTLE_MS`, двухкадровую проверку, `predictedImpact`, ROI/TTL/epoch. Изменение позволено только с отрицательными тестами анимации и отсутствия фактического действия. Ускорение 2–2.5× из пользовательского текста **не доказано**.

## Приоритет B. Новый `STACK_TOWER` (возможная механика Котобашни)

Документ сообщает о центральном персонаже и горизонтальных брёвнах/рулонах слева/справа. Это ещё не подтверждённая спецификация игры и не доказательство, что оно совпадает с прежней «Котобашней».

**Двухэтапная реализация:** (1) detector-only: искать центральную опорную область, обе стороны, движущиеся блоки и скорость по 3+ свежим кадрам, классифицировать неизвестное; (2) только по физическому подтверждению момента прыжка и безопасной зоны внедрять TAP с прогнозом времени столкновения. Не зашивать 120–160мс как истинную физику. Нужно измерить latency frame→gesture→game reaction; не обещать «50 из 50». Отдельный новый профиль/Adapter с поддержкой STOP/ROI, без подмены уже работающих Arcades.

**Приёмка:** размеченные реальные кадры из видео, detector precision/recall, симуляторные логи missed/early/late TAP, затем пять реальных визуально подтверждённых циклов.

## Приоритет B. Новый `HEXA_SORT` (возможная механика Гексона)

Документ сообщает 10 ромбовидно расположенных гекс-слотов и 3 нижние стопки, где важен *верхний* цвет. Позиции могут зависеть от экрана, прогресса, уровня и масштаба, поэтому «фиксированная геометрия» допустима только после привязки ROI и автоизмерения центров, а не на абсолютном дисплее.

**Этап 1:** read-only detector гекс-координат/пустоты/высоты/верхнего цвета плюс статус confidence на реальном кадре. Этап 2: solver с симуляцией размещения, механики слияния/переполнения, только потом drag нижней стопки на проверенную цель. Сохранять отдельные tracker-слоты и цвета; не направлять жест по неизвестному гексу.

**Приёмка:** распознавание 10 игровых ячеек и 3 нижних слотов на нескольких раундах/ориентациях, отрицательные кейсы разных верхних цветов и «занят», тест сохранения координат, пять подтверждённых drag без пропуска физики.

## Приоритет C. Опциональный авто-рестарт (до 5)

Существующий `GameOverScreen.detect` возвращает **boolean** и выявляет широкий жёлтый участок на белой карточке по пикселям, **не возвращая безопасные bounds конкретной кнопки «Играть снова» и не подтверждая её текст**. Следовательно, автоматический TAP по предполагаемому y над рекламой сейчас запрещён.

Для реализации: отдельный локатор целевой кнопки с однозначными границами и отличением от реклам/покупок; подтверждение той же карточки на двух свежих кадрах; отдельное явно включаемое ограничение `maxRoundReplays<=5`; STOP/window/fresh-ticket/permit/TTL; после TAP ждать исчезновения карточки и нового игрового состояния. Не нажимать при ambiguity, нестабильном ROI, защищённом окне, рекламе/платеже или вне безопасной геометрии.

## Очередность и правила принятия PR

1. **Сначала P0 стабилизация:** PR #55 с уроком из реального экспорта grid-палитры, Android build+emulator PASS, физический отклик и накопление обучения; не считать Action ACK успехом.
2. Отдельный PR для `SceneSignature` в режиме read-only/STOP и без автоматического full-screen ROI.
3. Отдельный PR для Debug HUD с доказанным исключением из захвата; предпочтительно наблюдаемая проблема неизвестных клеток/пушки.
4. Профили `STACK_TOWER` и `HEXA_SORT` после получения кадров/видео и разметки, отдельно друг от друга.
5. Ускорение по независимым end-to-end traces; авто-рестарт последним, после нового button locator.

**Всегда сохранять** `ActionGate`, `InputPermit`, fail-closed STOP, точные bounds/ROI, TTL, единственный executor, отличать ACK и визуальное подтверждение, protected-skull swap для 6×6, запрет выдуманных UNKNOWN. Не публиковать личные видео/архивы.
